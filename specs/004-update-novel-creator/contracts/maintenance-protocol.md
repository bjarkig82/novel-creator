# Maintenance and Release Protocol

## Controller/target boundary

The external controller owns all mutations. The target package advertises `update-release.json` protocol version 1 and exports its bundle using the existing installer inventory in a separate isolated process. The controller supplies fixed helper code through an argv subprocess boundary, not shell interpolation or a command read from book files. Export produces canonical relative paths, regular-file modes, base64 bytes and checksums; reject traversal, duplicate names, reparse points, foreign paths and mismatches with wheel contents.

Preparation runs the private venv interpreter with isolated pip and `install --ignore-installed --no-index --no-deps --no-compile` against the verified absolute wheel path. Reusing dependency packages does not permit inheriting the product package. Before export/probes, verify the product package resolves inside the private venv's site-packages and its module/resource byte inventory matches the selected wheel. Recheck all loaded product module origins and exported inventory afterward. Reject external origins, extra product files or changed resources before book mutation; never fall back to a same-version controller/base installation. Preserve the inherited installation unchanged and test a non-editable same-version inherited package with deliberately different bytes.

Use `-I -B` for the target children and a sanitized pip subprocess environment with `PIP_CONFIG_FILE=os.devnull`; configuration must not redirect installation into another prefix/target. `--no-compile` prevents generated bytecode from undermining the exact product inventory. Assert the install destination and inherited-package before/after hashes in the preparation tests.

Target compatibility probes receive immutable committed exchange envelopes and existing retrospective JSON over local stdin. Validate sequences/digests/record references and schema versions without a book path, grant registry, notice API or network transport. Do not cache private story payloads. Only operational success/schema diagnostics return. Existing committed records remain authoritative; probes cannot repair them.

After replacement, a controller-owned verification path may perform read-only installed imports/context validation while the maintenance fence remains held. This path is internal, validates operation token and actual candidate state, and must not be an exported bypass for saves, retro calls or general command execution.

## Controller functions

- `preview(novel, *, version=None, python=None, transport=None) -> result`: read-only book validation and external preparation. `python` is the explicit absolute interpreter from CLI `--python`, defaulting to the controller's `sys.executable` when omitted.
- `apply(novel, *, preview_id, version, expected_head, confirm_quiescent=False, fault=None) -> result`: exact reviewed operation.
- `status(novel, *, operation_id=None) -> result`: local read-only observation, implemented in the initial US1 controller before its CLI route. Cover no operation, pending, actual candidate publication/cleanup, conflict (including unproven ownership) and complete state without creating directories or contacting a release service.
- `recover(novel, *, operation_id, retry=False, expected_head=None, fault=None) -> result`: inspect or explicitly continue the exact operation.

`transport` and `fault` are test injection boundaries; production CLI cannot choose arbitrary release servers or fault points. Release acquisition lives in `update_release.py`, durable state/transaction in `update.py`, common exclusion in `maintenance.py`. Direct services enforce maintenance checks, not just CLI parsing.

Resolve and probe `python` before preparing the private target venv. Pass the resolved interpreter explicitly to release preparation and compatibility probes; return it as `data.runtime_python` and bind it with its dependency fingerprint into the preview and journal. Apply/recovery consume that stored interpreter and revalidate it, rather than silently substituting the controller interpreter or accepting an override. A test must use distinct controller and selected-interpreter paths to prove propagation end to end.

US3 recovery inspection consumes the same read-only status/evidence inspection implemented in US1 and adds retry-eligibility checks. It does not defer or reimplement the public status service. Synthetic journals and refs exercise every public status observation in US1; real interrupted-operation tests later verify the same inspector against the implemented transaction.

## Lock order and compatibility fences

Acquire nonblockingly in this order; release temporary locks in reverse order. Abort/release on contention before modifying installed files.

1. Exclusive book maintenance lease at `local/update/access.guard`. Ordinary operations hold shared leases, so normal contribution revocation remains independent of in-flight contribution work; maintenance excludes all such leases nonblockingly.
2. Exclusive persistent `.novel-creator/local/write.lock`, with an updater-specific operation token/owner journal binding. Refuse an existing unrelated writer lock.
3. Existing local retro `state.lock.guard`, then `authorization.lock.guard`.
4. Existing retro `runs/<UUID>.lock.guard` in sorted UUID order while state coordination prevents creating new run IDs.
5. Only for an existing valid enabled grant, the configured framework's `novel-creator-retro/inspection.guard`, without acquiring/releasing contributor `operation.lock` ownership or making GitHub calls.

Read grant/run state again after exclusions and refuse nonterminal work, uncertain external state, reserved notices or terminal cleanup. Disabled/unbound grants must not trigger external checkout access; if retained local evidence cannot establish safe inactivity, refuse and request separately authorized contributor recovery. Never call enable/disable/resume/release as an updater probe.

Future runtimes check durable active-update state before import/dispatch and inside direct save/recover, initialization continuation, context and retrospective service entrypoints. Read-only update status is always available from the external controller; book context may be paused while modules are mixed. The retro guard precedes its error-journaling handler, so a maintenance refusal cannot create a run failure or notice. Pure read-only retro status may remain available only from a verified consistent runtime.

## Durability and interrupted legacy clients

Persist a prepared operation with its intended fence token before acquiring the durable fence. Create the legacy writer-lock directory exclusively, then atomically write and durably flush its ownership metadata and parent directory. Durably transition the journal to `fenced` with `ownership_confirmed: true` only after those flushes. Matching metadata plus that confirmed checkpoint proves ownership; intent in a `prepared` journal alone does not. Do not change the launcher, imported product files, index or branch before this ownership checkpoint.

If the process stops after directory creation but before that checkpoint, classify the fence as `ownership_unproven`, report exit 6 with a preserve-and-inspect instruction and retain the directory/journal. Retry must not adopt, remove or rewrite that directory even if an owner file contains the intended token but the confirmed journal checkpoint is absent, or the former PID appears dead. This is an explicit blocked recovery outcome with unchanged installed files, not successful automatic recovery. An operator can investigate separately; the updater exposes no force-delete route. Test hard stops before ownership-file publication, before its flush and before the confirmed journal transition.

After proven ownership, swap the standalone launcher atomically before replacing imported product files. Do not use ordinary `writer_lock()` finalization to discard an incomplete update's persistent fence.

On interruption retain the writer fence and launcher gate; OS advisory guards release naturally. Recover only a fence whose operation token and journal match a durable `ownership_confirmed: true` checkpoint, with owner death positively established and expected HEAD validated. Without that checkpoint the outcome is the unproven-ownership blocker above, even if metadata happens to match. PID reuse or uncertain liveness is a blocker. No age-based takeover or arbitrary lock deletion.

Legacy in-memory clients cannot check a marker they predate. FR-009 requires all other book clients to stay closed throughout initial bootstrap and external recovery, then restart through the guarded launcher. Retain the lock bridge for live contention, but do not claim its automatically released OS locks protect arbitrary preloaded legacy clients after a crash. Test the supported fresh-launch lifecycle and the unsupported already-loaded case separately, as required by SC-005 and [FUP-001](../follow-ups.md). Confirmation never substitutes for lock checks or process evidence.

## Git publication and recovery

Build a private index from the previewed HEAD, update only verified framework/shared-rule paths and construct the candidate using `write-tree`/`commit-tree`. Candidate parent must be the reviewed HEAD; no story paths or unrelated index entries may differ. New bytes are journaled before writes; absent/add/remove paths use explicit expected-before checks.

Before conditional `update-ref`, recheck branch, affected index baseline and complete target worktree inventory, allowing only the recorded temporary launcher at its fixed path. Publication uses the original HEAD as compare-and-swap predecessor. If publication fails or branch changed, retain evidence and stop.

Synchronize only affected entries under the real index lock, starting from the latest full index so unrelated staging survives. Removed resources emit mode-zero deletion records; factor this into the current `sync_index()` without changing ordinary save behavior. A partially staged shared file that needs modification blocks preview/application rather than being flattened.

Recover pending state only when HEAD equals the reviewed parent; recover published state only when HEAD equals the exact candidate. Refuse other HEADs or changed evidence. Complete resource/index/read-only verification, restore the final launcher, record completion and release the owned fence. If fence release fails, remain cleanup-needed. There is no reset, history amendment, automatic rollback, story exchange or new commit after candidate publication.
