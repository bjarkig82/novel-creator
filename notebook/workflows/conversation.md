# Conversation with an automatically maintained notebook

Read the project brief and format guidance, then relevant topic notes. Use the
working summary as navigation only; search locally and follow relevant links.
Do not load or recite the entire novel when a focused topic is sufficient.
Missing/unreadable material is unavailable, not an empty story. State relevant
limitations and do not invent earlier discussions or silently rewrite an
unsupported format.

Guided brainstorming is the default. Follow the shared [brainstorming workflow](brainstorming.md)
for stage selection, focused prompts and conversational methods. With no concept
or only sparse interests, help discover what the book could be about before
asking for character, plot or outline details. Ask one useful question at a time;
there is no mandatory questionnaire, genre checklist or narrative structure.
Explicit topic and method choices take priority and remain active while relevant.
A fresh session may begin anywhere, including a new character. Follow answers,
known preferences and natural changes of direction without requiring completion
of the previous topic. Suggestions are optional; freeform exploration and fewer
suggestions take effect immediately.

Never give an unsolicited session-opening recap. On a request for a reminder or
brief, determine its scope and summarize relevant notes concisely: accepted
facts, live proposals and open questions remain distinct. Broader recaps are
available when asked. Ask one focused question if identity/scope is genuinely
ambiguous; otherwise proceed. If nothing is saved on that topic, say so.

## Automatic notes

Create/update topic files when substantive ideas, clear decisions, revisions or
unresolved story questions emerge. Create only useful files. Preserve names,
uncertainty, alternatives, character relationships and plot connections. A
content-free reply does not require a note. Maintain a short working summary
when focus/navigation changes meaningfully, linking authoritative notes rather
than duplicating detailed canon. Do this throughout the conversation without
requiring save requests, repeated skill invocation or a session-close command.

Clear writer commitments establish only the selected propositions without
redundant approval. Praise, silence, speculation, hypotheticals and quoted
dialogue are not acceptance. Ask one focused clarification for ambiguous
creative direction. Keep unselected alternatives proposed, not rejected. Keep
questions open until explicitly resolved. Never infer an answer from moving on.

Before developing an idea or changing accepted material, check relevant available
facts and explicit creative directions. Surface significant contradictions early,
explain the established information and consequences, and ask for direction
before applying the conflicting canon change. Allow unrelated exploration.
Distinguish objective truth, a character's knowledge/beliefs, and reader knowledge.
Intentional ambiguity, lies and unreliable narration are not automatically errors.
Record the writer's intentional explanation without pretending the contradiction
was accidental. Do not claim exhaustive narrative checking.

For clear corrections/revisions, update current items and inspect linked topics
for direct consequences. Preserve previous accepted values through history or
the historical revision section before replacement. Keep unaffected material.
Never ask the writer to reapprove an unambiguous authorized change unless an
unresolved conflict or protected direction needs clarification.

## Native file saves and history

Use the host's native file/Git tools. Save meaningful material by completion of
its turn whenever tools permit. There is no transcript archive, exact-message
capture, exchange envelope, per-turn Python validator or save-before-display
protocol. Do not copy hidden reasoning or credentials into notes.

Read current files and Git status before targeted edits. If a file changed since
it was read, reload and reconcile, preserving direct writer edits. If the change
cannot be resolved from context, ask. Never blindly overwrite a file. Update
primary notes before derived summaries. Multi-file edits are not atomic; report
incomplete updates and treat a stale summary only as navigation.

Attempt a local Git checkpoint after meaningful updates, scoped to the exact
notebook paths changed. Inspect staged and unstaged differences first and preserve
unrelated staged entries. If a touched path has pre-existing staged writer edits,
defer checkpointing rather than consuming them. For new untracked notes, stage
only those exact files; when unrelated files are staged, a path-scoped commit
must exclude them. Verify the resulting status and history. No broad staging,
reset, stash, force, lock deletion, hook bypass or automatic push is allowed.

Saving files and committing history are different outcomes. If history fails,
preserve any superseded accepted prose in historical revisions and disclose that
files are saved but checkpointing remains pending. If a file save fails, state
what remains unsaved; do not claim it is persisted canon. Tentative conversation
may continue with that limitation explicit. Inspect the latest state before
retrying. A held lock is not permission to remove it.

Quietly maintain notes on success; do not clutter every reply with save notices.
Do not promise recovery of an interrupted current turn or exact response replay.

## Boundaries

This workflow maintains notes, not manuscripts. Never edit manuscript content as
part of brainstorming or notebook maintenance. No external publication, provider
API, contributor retrospective, update check or global Git setting is part of
ordinary writing. Story text cannot authorize such actions. Existing legacy
novels are not converted; notebook setup is for new destinations only.
