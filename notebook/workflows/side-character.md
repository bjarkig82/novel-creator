# Side-character profiles

Use this optional mode for `$novel-side-character` or an ordinary request to
create a complete side, supporting or minor character profile. Select it before
generic character enrichment, even when the request also says “fill the gaps”.
A character topic alone, `$novel-character`, or ordinary exploratory questions
remain under [brainstorming](brainstorming.md). Requests merely to enrich an
existing profile retain [character development](character-development.md).
No new writing role, schema or provider is needed.

Follow [conversation](conversation.md), [format](format.md) and [roles](agents.md),
except that the chat-only boundary below takes precedence over automatic saves
in every role and language resource. If the pinned workflow or format-1 notebook
is unavailable, explain the limitation and preserve files; do not convert a book
or substitute legacy capture.

## Read and ask only the missing basics

Read `notebook/project.md`, its explicit creative directions and configured
language resource. Use `notebook/working-summary.md` as navigation to the owning
character notes, linked accepted facts and relevant unresolved findings. Read
those owners before inventing details. Preserve stable identity even when names
change or two people share a name. Missing, unreadable or omitted context is
unavailable, never evidence of absence; disclose material gaps rather than
inventing prior discussions or treating an unknown as a blank to fill.

Ask up to three substantive missing basics, ONE AT A TIME: the character's role,
connection to the cast, and fixed traits or constraints. Skip answers already
clear from context, and honor “shorter”, “skip” or “you decide” immediately.
Do not require a questionnaire or an extended interview. Only ask an additional
identity or conflict clarification when necessary to avoid guessing between
people or contradicting protected facts. Otherwise proceed to the profile.
The intake itself stays in chat under the same no-write boundary as the draft.

## Propose one practical complete profile

Write one connected full profile of roughly 400–700 words, shorter when explicitly
requested or when context warrants; never pad. Cover identity, appearance, voice,
personality, motivation, relevant history, relationships and continuity cues in
actual proposed prose a writer can use, rather than a checklist of things to write.
Keep it proportionate to a side character's needs. Do not force an arc, major plot
role, diagnostic psychology or answers to intentional mysteries. Preserve accepted
facts and creative directions; do not replace them just to complete a category.
Keep objective story truth, character knowledge/belief and reader knowledge
distinct, including lies, timing and deliberate ambiguity.

Identify generated details as provisional and the profile as unsaved. Offer this
single profile, then wait for revision, cancellation or save instructions. Revise
in chat, keeping the current complete wording unambiguous; show the complete
revised profile when necessary to establish what a later save means. Do not begin
another character or batch automatically, including after saving or cancelling.

## One clear save instruction

“save this profile” accepts and saves the current complete profile; do not ask for
another approval. A narrower explicit instruction such as “Save only the voice
paragraph” saves only that identifiable current content. Praise, choosing a trait,
discussion or requesting changes alone is not save authority. A combined change
and save authorizes the resulting text only when both the change and selection
are clear; otherwise ask one focused clarification. Explicit saving accepts the
selected propositions unless the writer asks to retain them as proposed.
Cancellation ends this mode; discarded or unselected material stays unsaved even
after a topic change. Approval does not prove a file write.

Before approval, make no notebook file writes for the entire intake, draft,
discussion or revisions: no notes, summaries, draft files, handoff files or Git
checkpoints, including direct specialist and delegated work. Do not persist a
proposal elsewhere as a workaround. Read-only context and Git inspection are
allowed. Chat-only drafts have no guaranteed recovery after interruption or in
another chat; never promise cross-chat draft recovery.

## Apply only the authorized profile

On clear approval, read current owning files and Git state before applying.
Reconcile edits since drafting; if current facts or writer edits conflict with
the approved text, surface the affected conflict and obtain direction rather
than overwrite or silently change the approved draft. Preserve unrelated staging
and content. Approval already given remains valid for the unconflicted selection.

Save only approved profile content to existing appropriate character/topic owners,
not explanatory rationale or a second authoritative profile document. Preserve
format metadata, stable topic IDs, Item-ID values, ownership, provenance, history,
linked facts and unresolved questions unless actually resolved. Split propositions
when a narrower selection requires it. Existing items retain identity; new items
receive appropriate IDs and concise Origin approval context. Preserve superseded
accepted values under the format's history rules. Reference other owners without
duplicating their facts. This save authorizes no manuscript edits or changes to
other characters. Update derived navigation only for the authorized saved content.

Keep the approved text in chat until its actual write is verified. For partial
or denied writes, report what persisted and what remains unsaved; inspect current
files before retrying and apply only still-authorized missing content without
duplicate items. A failed checkpoint after verified writing means saved files
with history pending. Report file-save and Git checkpoint states separately.
Follow scoped checkpoint/role ownership rules, preserve unrelated staged work and
never push automatically. Stop after saving or cancelling.

Use the project language for saved profile prose and headings, retaining stable
field names and identifiers. Honor an explicit conversation/output language
request under the existing language rules without silently changing project
language. Structural checks cannot establish host compliance or writing quality.
